「北捷輿情日誌」是怎麼自己跑起來的？

你每天收到的那則推播通知，背後其實是一整條無人值守的生產線：排程觸發、AI 讀資料、上網蒐集新聞、寫回資料庫、組頁面、驗證、雙軌上線、推播回報。這篇文件用「捷運路網」的方式，把這條線從頭到尾攤開給你看。

閱讀時間 約 10 分鐘 · 對象：不寫程式的 PM / 營運 · 版本 2026-09-21
30 秒版本

這是一個「每天自動醒來一次」的 AI 任務。它醒來後會：讀取昨天寫好的資料 → 上網找今天跟台北捷運有關的新聞與討論 → 把新資料寫進一份 JSON 清單 → 用同一份清單組出兩個網頁 → 用真的瀏覽器截圖檢查版面沒壞 → 同時發布到「Claude Artifact」和「GitHub Pages」兩個地方 → 傳一則通知告訴你今天發生了什麼。

你不需要碰任何程式碼。你需要知道的只是：「排程」決定什麼時候跑、「Artifact」和「GitHub」是兩個不同的家，但住的是同一份內容、「LOG 陣列」是這整個系統唯一的資料庫。

02

名詞小辭典

跟「AI 怎麼運作」有關

Routine（排程任務）schedule

你在後台設定好的鬧鐘，例如「每天早上跑一次」。時間一到，系統會自動開一個全新的對話，把固定的任務指令丟給它，不需要你手動點「開始」。

Session（對話）session

Routine 每次觸發，都是一個「全新的人」在做事——它沒有昨天的記憶，完全靠讀取「昨天留下的檔案」來接手，這也是為什麼整個系統必須把狀態都存在檔案裡，而不是存在 AI 的腦袋裡。

Skill（技能包）skill

一份預先寫好的「操作手冊」，AI 在需要時會臨時讀進來照著做，例如「怎麼設計一個好看的網頁」。用完即丟，不佔用平常的思考空間。

WebSearch / WebFetch工具

AI 用來上網的兩隻手：WebSearch 像 Google 搜尋，先找「有哪些相關頁面」；WebFetch 則是打開某一個網址、把內容讀進來整理給你。今天蒐集新聞用的就是這兩個工具。

跟「網頁怎麼組出來」有關

LOG 陣列data

整個系統唯一的「資料庫」——其實就是網頁原始碼裡的一段 JSON 清單，每一天是一筆資料，裡面放著當天的新聞條目。沒有 MySQL、沒有後端，資料就直接寫死在網頁裡。

JSON格式

一種「用大括號和方括號包資料」的通用格式，幾乎所有系統都看得懂。你可以把它想成「結構化的 Excel 表格」，只是用純文字寫成。

Playwright工具

一支「假裝成使用者」的自動化瀏覽器。AI 用它打開剛做好的網頁、拍下截圖，藉此檢查版面有沒有跑掉、按鈕能不能點——這是發布前唯一的「人工測試」替代品。

Chromium瀏覽器核心

Google Chrome 背後的引擎，Playwright 就是拿這顆引擎去開網頁。伺服器上沒有真的視窗，所以是「看不見畫面、但真的有在跑」的無頭（headless）瀏覽器。

跟「GitHub / 上線」有關

Repository（repo）倉庫

一個專案的完整檔案總管，這次是 cjw9223233/mrt-log。所有版本紀錄、每次修改，都存在這裡。

Commit / Push版控動作

Commit 是「幫這次修改拍一張快照、寫一句說明」；Push 是「把這張快照上傳到 GitHub 的伺服器」。沒有 Push，修改只存在本機，別人看不到。

Branch（分支）分身

同一個 repo 可以有好幾條平行時空。main 是正式對外的那一條，claude/xxx 是這次任務專用的工作分支。這次因為要直接上線，兩條分支都會收到同一個 commit。

GitHub Pages免費架站

GitHub 提供的免費服務：只要 repo 裡有一個 index.html，它就會自動把整個 repo 變成一個公開網站，網址通常長得像 帳號.github.io/repo名稱。

ArtifactClaude 的頁面

Claude 這邊自己的「快速發布網頁」功能，跟 GitHub 無關，發布後會拿到一個 claude.ai 開頭的連結，可以直接分享給任何人開啟，不需要懂技術。

MCP / Connector外部接線

讓 AI 能操作外部服務（例如 GitHub）的「轉接頭」。這次能自動 push 程式碼到 GitHub，靠的就是背後接好的 GitHub 授權，不需要人工輸入帳密。

跟「回報」有關

PushNotification推播

任務跑完後，主動把重點推到你的手機或信箱的工具。設計原則是「沒事不打擾」——平淡無事的一天可以選擇不推播，只在真的有東西值得你知道時才響。

Egress Proxy（對外連線代理）網路限制

這次任務跑在一個受管控的環境裡，對外連線會先經過一層「代理」把關，某些網域（例如 metro.taipei、github.io）會被擋下無法直接讀取，這是安全設計，不是故障。

03

逐站說明：這條線實際怎麼跑

STOP 1

讀基底：先找「昨天寫到哪」

Session 一啟動，第一件事不是找新聞，而是先把「昨天最後長什麼樣子」讀進來——優先讀 Claude Artifact 那份，讀不到才改讀 GitHub 上的 index.html 當備援。兩邊都讀得到時，會比對哪邊資料比較新、比較完整。

今天實際情況：Artifact 讀取成功，且發現裡面已經有「今天」這一天的資料——代表這是同一天內的第二次執行，於是切換成「補資料」模式，而不是「新增一天」。
STOP 2

蒐集：上網找今天的真實素材

用 WebSearch／WebFetch 分頭查詢新聞網站、PTT 討論板、官方新聞稿頁、誤點證明頁，盡量涵蓋「營運狀況、工程進度、票務政策、治安安全、社群熱議」五大類。找到的每一則都要留下可點擊的原始連結，不能只憑印象生成內容。

今天實際情況：查了貓纜狀態、萬大線施工爭議、中捷藍線預算攻防等多個關鍵字，確認除了早上已記錄的 12 則之外，沒有新的重大事件，所以沒有新增條目。
STOP 3

寫入：塞進 LOG 這份「假資料庫」

把整理好的素材，依照固定欄位格式（分類、熱度、標籤、摘要、來源連結）寫成一筆 JSON 物件。這個系統沒有真的資料庫，LOG 陣列本身就是資料庫——整份歷史，就活在網頁原始碼裡的那一段文字裡。

今天實際情況：因為是同一天重跑且沒有新素材，只更新了頁首「最後更新」時間戳，LOG 陣列的內容維持不變。
STOP 4

組頁：一份資料、兩種外殼

同一段 LOG 資料，會被包成兩個不同的檔案：一個保留 Artifact 平台加的外框，另一個組成完全獨立、可以放在任何網站的標準 HTML 檔（給 GitHub Pages 用）。版面的 CSS、排版邏輯完全不動，這一步只換「外殼」，不碰設計。

今天實際情況：用 sed 把原始檔案從 <title> 到 </script> 這一段抽出來，前後補上標準網頁該有的 <!doctype>、<head>、<body>，變成獨立的 index.html。
STOP 5

驗證：機器自己先當一次讀者

在真正發布之前，用 Node.js 把 LOG 陣列抽出來實際「解析」一遍，確認格式沒寫錯、日期沒重複、天數沒超過上限；再用 Playwright 開一個看不見的瀏覽器把頁面整個跑一次，截圖檢查排版，並且真的去點「切換日期」「雙日比對」這些按鈕，確認功能沒壞掉。

今天實際情況：解析結果確認共 14 天資料、日期由新到舊排列、今天 12 則、所有連結都是合法網址；截圖確認主頁與雙日比對畫面都正常顯示。
STOP 6

上線：同時部署到兩個家

驗證過關後，兩邊幾乎同時發布：GitHub 那邊用 git commit + git push 把新的 index.html 送上 main 分支，觸發 GitHub Pages 自動重新部署公開網站；Artifact 那邊則用同一個網址「覆蓋更新」，版本號自動往上加一，舊網址不會變。

今天實際情況：這是這個 repo 第一次真的有 index.html 被推上去（之前只有一份 README）。Artifact 端則是已經第 31 個版本，代表這條線已經穩定跑了一個多月。
STOP 7

回報：只在值得的時候打擾你

最後一步是決定「要不要通知你」。系統被設計成預設安靜：如果今天沒有新東西、兩邊都部署成功，可以選擇不發通知，避免每天洗版一則「一切正常」。只有出現新的重要事件、或部署過程有異常需要你知道時，才會真的推播。

今天實際情況：因為是「repo 第一次真正上線」這種一次性的里程碑，判斷值得讓你知道，所以還是發了一則通知，並附上兩個連結。
04

為什麼要這樣設計？

為什麼要同時發布到 Artifact 和 GitHub 兩個地方，不是重複做工嗎？
兩者服務的對象不同。Artifact 連結誰都能打開、不需要懂技術，適合快速分享；GitHub Pages 則是「真正屬於你、掛在你自己網域下」的公開網站，之後要接自訂網域、串其他自動化都比較有彈性。用同一份 LOG 資料組出兩個外殼，維護成本幾乎沒有增加。
為什麼「同一天重跑」要用「補資料」而不是「新增一筆」？
因為 Routine 可能一天觸發不只一次（例如人工手動又跑了一次，或排程設定成每天兩次）。如果每次都新增一筆，日期欄位就會重複，網頁上的「切換日期」清單會出現兩個一模一樣的 09-21。所以系統會先檢查陣列裡有沒有今天的日期，有的話就地補充，維持「一天只有一筆資料」的規則。
為什麼發布前要特地開瀏覽器截圖，而不是看程式碼有沒有報錯就好？
程式碼「沒有報錯」不代表「排版沒有跑掉」——欄位塞太長的文字、CSS 選錯顏色，這些問題只有實際「用眼睛看畫面」才抓得到。Playwright 截圖加上實際點擊按鈕測試，是目前最接近「找一個人幫你點開來看一眼」的自動化做法。
為什麼有些官方網站（例如 metro.taipei）AI 讀不到？
這個執行環境的對外連線會先經過一層「Egress Proxy」把關，只放行特定名單內的網域，其餘一律擋下——這是資安上的保護機制，避免自動化任務任意存取或洩漏資料到未知的外部服務。遇到這種情況，系統會改用搜尋引擎的摘要結果來間接取得資訊，不會因此整個任務失敗。
05

萬一出狀況，通常是這些原因

症狀最可能的原因系統怎麼自己處理
git push 被拒絕repo 對 main 分支設了保護規則，不接受直接推送改推到一條備用分支，並在通知裡請你去 GitHub Pages 設定把來源分支切過去
Artifact 發布失敗這次的基底資料來自 GitHub 備援版本，系統認定「還沒讀過最新的 Artifact 版本」，為了避免覆蓋掉別人剛改的內容而擋下因為已經先確認 GitHub 版才是最新、最正確的版本，會用「強制覆蓋」參數完成發布
出現「repo 尚未授權」錯誤這個 Routine 目前只被允許操作特定幾個 repo，這次要處理的 repo 不在名單裡不會嘗試繞過權限限制，只會照常做完其他能做的事，並在通知裡請你去後台把這個 repo 加進允許名單
公開網站看起來還沒更新GitHub Pages 從收到新檔案到全球生效，本來就有幾分鐘的快取延遲會嘗試重新讀取確認，讀不到不會直接判定失敗，只會在通知裡註記「可能還在生效中」
06

身為 PM，你真正需要記得的三件事

01

你不用管程式碼

這整條線平常完全不需要人工介入。你唯一會接觸到的，是收到的推播通知、以及兩個最終網址。

02

資料只有一份，別自己手改

LOG 陣列是唯一真相來源。如果你想調整內容或修正錯字，最安全的做法是請 AI 依照同樣的格式規則去改，而不是直接在網頁上手動編輯，避免下次自動更新時把你的修改蓋掉。

03

沒收到通知＝一切正常

這是刻意的設計，不是系統壞掉忘記通知你。如果你想確認狀態，直接打開兩個公開連結看「最後更新」時間戳，會比等通知更即時。
